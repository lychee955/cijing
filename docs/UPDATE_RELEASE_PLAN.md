# GitHub Releases 分发与跨平台更新实施方案

日期：2026-10-03。

状态：已实施主进程更新服务、品牌区界面、Windows x64 打包与本地元数据校验。2026-10-05 更新检测改为读取源码仓库 `updates/stable.json`，检查阶段不再查询 GitHub Releases REST API 或 `latest.yml`；清单生成与公告流程见 [静态更新清单](../updates/README.md)。自动安装仍受签名和实机验收开关保护；当前代码为快照开发版 0.0.2-snapshot.20261004.1；真实旧版升级尚未验收，以 Pre-release 分发快照，尚无正式版。实施结果见 [UPDATE_RELEASE_ACCEPTANCE.md](UPDATE_RELEASE_ACCEPTANCE.md)，发布操作见 [RELEASING.md](RELEASING.md)。下文保留原设计与实施前基线，其中正式 Release API 检测方案已由静态清单替代。

## 1. 目标与范围

在品牌 Logo 下方增加版本与更新入口，通过 GitHub Releases 分发软件，并判断是否存在适用于当前客户端的新版本。

首期支持 Windows x64：NSIS 安装版支持用户确认下载、重启安装；便携版支持发现新版并跳转下载。设计保留 macOS、其他架构及安装形式的扩展能力，未验收的组合不得启用自动安装。

默认采用公开仓库 `lychee955/cijing`。正式实施时核实 Release 是否可匿名读取；如果代码仓库私有，优先另设公开分发仓库，不把发布 Token 放入客户端。

本期不包括强制升级、静默安装、自动降级、跨架构切换、Linux 安装实现和真实 macOS 发布。GitHub Actions 自动发布列为后续阶段，不阻塞首次手动发布。

## 3. 更新判定规则

可更新条件：远端版本高于本地版本，符合当前更新渠道，且存在与当前平台、应用架构、安装形式和最低系统要求兼容的更新包。

### 3.1 本地环境

- 版本从 `app.getVersion()` 读取，唯一来源为构建时的 package.json。
- 系统使用 Electron/Node 平台标识，例如 `win32`、`darwin`。
- 架构以当前应用的构建/运行架构为基础，保留 x64、arm64、universal 匹配能力；不单凭物理 CPU 推断应下载的包。
- 安装形式区分 NSIS、portable、macOS app、开发运行及未识别形式。使用打包标记与平台能力探测，并在实际产物中验证；不得把所有 Windows EXE 都视作 NSIS。
- 开发模式不访问正式更新源、不安装更新。测试通过注入模拟更新服务完成。
- Universal 是发行包属性，不是直接期望从 `process.arch` 读取的值。macOS 阶段再验收原生 ARM、Intel 和 Rosetta 的选择策略。

### 3.2 远端信息与比较

1. 主进程访问固定 GitHub 分发仓库，读取正式 Release 及对应平台更新元数据。
2. 使用成熟语义版本库/更新组件比较版本，禁止字符串比较。`0.10.0` 高于 `0.9.0`，相同版本替换附件不算更新。
3. 正式客户端忽略草稿与预发布版本；首期不提供用户切换渠道的入口，模型中保留渠道字段。
4. 校验目标文件与当前平台、架构、安装形式匹配后才进入可更新状态。不能直接把原始 `update-available` 事件无条件转发给界面。
5. 下载前再次核对候选版本、目标文件和更新组件实际选择结果，下载后由更新组件校验文件；信息不一致时停止安装并提示重试。

使用 electron-builder 生成的元数据。Windows 通常为 `latest.yml`，macOS 通常为 `latest-mac.yml`；多架构文件组织及选择逻辑必须按最终锁定工具版本做打包实验，不假设 metadata 的每个条目都自带可靠的 arch 字段，也不认为在文件名添加架构就自动完成隔离。

### 3.3 缺包、检查失败与发布一致性

必须区分以下结果：

| 场景 | 结果 |
| --- | --- |
| 成功检查，适用渠道没有更高版本 | 已是该渠道的最新适用版本 |
| 有更高版本，但 Release 没有当前平台/架构的包 | 暂无适用于此设备的更新；不显示 NEW |
| 有目标安装包，但缺少所需更新元数据、元数据损坏或引用文件不存在 | 更新发布不完整；禁止安装 |
| 网络失败、GitHub 限流、超时、无法确认 Release 信息 | 检查失败；不能显示已是最新版 |
| 当前安装形式不支持自动安装 | 通过手动下载路径处理；不能调用自动安装 |

不能把单独一次 metadata 404 直接解释为“没有适用更新”。必要时查询同一 Release 的资产清单，区别未发布此平台和发布缺失；无法确认时保留检查失败。资产检查与 updater 的候选 Release 必须一致。

首期采用同一正式版本统一发布政策：每个正式 Release 应包含当时已支持平台的完整产物，上传完成后一次性公开。当前只要求 Windows；macOS 正式上线后将其加入发布完整性检查。

若后续需要 Windows 与 macOS 独立发布版本，先扩展候选版本解析和平台更新源，验证“仓库最新版本无 Mac 包，但较旧 Release 有更高的适用 Mac 版本”的选择行为，再启用独立发布。首期不承诺扫描历史 Release 自动回退找包，不能用仓库的全局 latest 等同于所有平台的最新适用版本。

### 3.4 能力矩阵

| 平台 / 应用架构 / 形式 | 首期能力 | 后续安排 |
| --- | --- | --- |
| Windows x64 NSIS | 检查、用户确认下载、重启安装 | 首期实机验收 |
| Windows x64 portable | 检查、打开对应 Release 下载页 | 不自替换运行中的 EXE |
| Windows arm64 | 暂不启用自动安装 | 增加产物、元数据隔离和实机验收 |
| macOS x64 / arm64 / universal | 类型与适配入口预留 | 签名、公证、DMG + ZIP、Mac 实机验收后启用 |
| Linux 或未知安装形式 | 明确暂不支持自动安装 | 单独增加适配与验收 |

## 4. Logo 下方的入口与交互

参考用户提供的 Logo 附近 NEW 提示，将入口放在现有顶部品牌区域下方，不改造成参考程序的整套侧栏布局。

| 状态 | 入口表现 | 点击行为 |
| --- | --- | --- |
| 尚未检查 / 无更新 | `v0.2.0` | 打开更新面板，可手动检查 |
| 检查中 | `正在检查更新…` | 查看状态，禁止重复发起 |
| 发现适用更新 | `NEW · v0.2.1 可更新` | 查看版本、更新说明和下载动作 |
| 下载中 | `下载更新 45%` | 查看进度 |
| 下载完成 | `重启并更新` | 检查业务是否空闲后安装 |
| 便携版发现更新 | `NEW · v0.2.1 可下载` | 查看说明并打开对应版本页面 |
| 无适用包 / 不支持 | 保留当前版本，不显示 NEW | 面板解释原因 |
| 检查或下载失败 | 保留当前版本及可重试提示 | 查看原因并重试 |

面板显示当前版本、目标版本、适用平台、发布日期、更新说明和最后检查时间。入口不挤占主导航，验收窄窗口、浅色、深色、键盘操作和焦点返回。

更新说明作为外部数据，以纯文本或关闭原始 HTML 的安全 Markdown 渲染。打开 Release 页面须由主进程验证 HTTPS、仓库及目标地址；渲染层不能传入任意下载地址或本地安装路径。

建议默认策略：启动后约 10 秒后台检查一次，持续运行每 6 小时检查一次；后台失败不弹窗，用户手动检查时给出明确结果。检查请求合并、设置超时、遵守限流等待时间，不做无限重试。休眠恢复不补发堆积请求。

仅由用户点击触发下载和安装。配置 `autoDownload = false`，并关闭默认退出时安装行为，避免下载后普通退出被误当作同意安装。下载期间允许继续使用业务功能。

## 5. 实现结构与边界

采用 electron-updater 处理受支持安装版的下载、校验和安装；项目自身负责设备能力、发布完整性、交互状态及业务退出协调。便携版使用同一发布来源和版本规则，但不复用 NSIS 安装动作。

| 建议文件 | 职责 |
| --- | --- |
| `src/shared/update.ts` | 平台、架构、安装形式、渠道、候选版本及状态类型 |
| `src/main/updates/environment.ts` | 识别运行环境与支持能力 |
| `src/main/updates/release-source.ts` | 固定仓库配置、Release 资产检查、便携版版本检测 |
| `src/main/updates/service.ts` | 检查调度、状态转换、并发合并和错误映射 |
| `src/main/updates/adapters/` | 安装版 updater 封装、便携版手动下载，以及后续平台适配 |
| `src/main/ipc/updates.ts` | 更新专用 IPC，复用现有来源和参数校验 |
| `src/shared/contracts.ts`、`src/preload/index.ts` | 暴露有限的更新操作与状态订阅 |
| `src/renderer/src/stores/updates.ts` | 接收主进程快照和状态通知 |
| `src/renderer/src/components/UpdateEntry.vue` | Logo 下方入口与更新面板 |
| `src/renderer/src/App.vue`、`style.css` | 品牌区接入与布局 |
| `electron-builder.yml`、`package.json` | 依赖、显式平台架构、产物命名、更新源和打包命令 |

IPC 拟提供 `status`、`check`、`download`、`install`、`openRelease` 和 `onChanged`。主进程持有候选版本和地址，调用方仅提交动作；状态包含能力、当前版本、目标版本、进度、最后成功检查时间及错误阶段。未知系统通过能力结果处理，界面不散落 `win32` 判断。

逻辑状态至少区分 idle、checking、upToDate、noCompatiblePackage、unsupported、available、downloading、downloaded、installing、error。失败时保留合法候选版本以便重试，过期检查和下载事件不能覆盖较新的状态。

更新日志单独记录检查、目标版本、平台、失败阶段及安装结果，不记录业务 Token 或 AI Key。GitHub 更新访问不携带现有业务鉴权信息。

## 6. 安装、退出与用户数据

保持 appId、包名和用户数据路径稳定。更新替换应用文件，不删除数据库、凭证或设置；便携版当前也使用用户数据目录，并非把数据放在 EXE 旁边。

安装前由主进程统一检查业务状态。当前 SessionService 请求计数和 AnalysisService 任务为内部状态，需增加只读忙碌查询或统一退出协调器，不能只凭界面按钮判断。

- 有添加、确认恢复、分析或翻译任务时，提示任务完成后再安装，不强行终止可能产生写入的操作。
- 通过安装检查后锁住新业务请求，避免检查空闲到退出之间的竞态。
- 明确进入更新退出流程，使关闭窗口不被隐藏到托盘逻辑拦截；不能假设 updater 与普通退出的事件顺序完全相同。
- 保存窗口状态、释放快捷键和托盘、完成数据库关闭，再由适配器触发安装。
- 验证安装失败后的重新启动和数据可读性，不能承诺自动回滚安装包或数据库。

若新版本包含数据库结构变更，单独增加迁移与备份恢复验收；未来结构版本可能无法被旧程序读取。问题版本原则上以更高版本修复，不启用自动降级。

## 7. GitHub Release 发布流程

### 7.1 首期手动发布

1. 增加并锁定兼容的 electron-updater 版本，明确 GitHub publish provider、owner、repo；客户端不包含发布凭证。
2. 将 Windows 首期目标固定为 x64，按平台和架构命名，例如 `cijing-0.2.1-win-x64-setup.exe`、`cijing-0.2.1-win-x64-portable.exe`。
3. 增加明确只打包不上传的命令，显式使用 `--publish never`；保留未来单独的发布命令，避免构建环境变量意外触发发布。
4. 提升 package.json 版本并同步 package-lock.json，完成必要检查，从本轮干净输出生成产物。
5. 验证安装包启动、原生 SQLite 加载、应用名/版本和用户数据路径。
6. 在对应 `vX.Y.Z` Tag 的 Release 草稿中上传本轮安装包、生成的 `.blockmap`、`latest.yml` 和便携包。元数据不手写校验值，不上传调试文件或旧包。
7. 校验元数据引用的文件全部存在，版本、架构、大小及校验值匹配，完成从旧版到新版的真实更新测试。
8. 写明变更内容与便携版更新方式，附件齐全后发布正式 Release。草稿无法代表匿名正式用户的端到端更新结果，测试应使用隔离分发仓库/测试源先验证，再检查正式发布结果。

`package.json` 的 `private: true` 只用于防止误发布 npm 包，不表示 GitHub 仓库必须私有。

不要修改已发布版本的二进制而保持版本号不变。打包输出与更新元数据始终作为一组管理。

### 7.2 后续 CI

增加独立发布工作流：Tag 版本校验 → 对应系统构建 → 各平台检查 → 汇总产物与元数据 → 创建或更新草稿 → 完整性检查 → 发布。

多架构任务不得各自上传同名 latest 文件并互相覆盖；先验证工具支持的合并产物或架构独立更新源方案，再增加矩阵。凭证放在仓库 Secrets/受限发布环境，日常测试无需写入 Release 权限。

## 8. macOS 扩展阶段

进入 Mac 阶段时单独完成以下工作后再启用自动安装能力：

1. 增加 macOS 构建环境与应用图标、稳定 bundle 标识、签名和公证流程。
2. 生成 DMG（首次安装）及 ZIP（更新所需产物），发布对应 Mac 更新元数据。
3. 决定 x64、arm64 分包还是 Universal；在 Intel、Apple Silicon 及必要的 Rosetta 场景验证选择结果。默认不自动跨架构迁移。
4. 验证 better-sqlite3 的目标架构、应用签名、系统加密凭证、安装位置权限、应用替换和重启行为。
5. 验证 Mac 安装新版本后凭证和历史保留，并检查最低 macOS 要求。
6. 把 Mac 产物纳入统一 Release 完整性检查；如果改用各平台独立版本，先完成第 3.3 节的更新源扩展。

Mac 功能尚未启用时，模拟测试只能证明分支与界面行为，不能标记为 macOS 实机更新通过。

## 9. 实施顺序与验收

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| A：打包与更新源验证 | 核实公开仓库；锁定工具版本；用两个版本验证元数据、目标选择和安装形式识别 | Windows x64 安装包链路可复现；记录多架构扩展约束 |
| B：主进程更新服务 | 环境识别、平台能力、Release 检查、状态机、下载与退出协调 | 模拟成功/失败及并发场景通过，无不适用更新安装 |
| C：品牌区界面 | 入口、面板、状态订阅、下载和安装动作 | Logo 下方布局、深浅色、窄窗口及键盘操作通过 |
| D：安装包验收 | 真实旧版到新版、便携版、数据保留、失败恢复 | 安装后版本正确，Token/AI 配置/历史可用 |
| E：发布文档与首发 | 完整产物清单、Release 说明、手动更新指引 | 可按文档复现发布，正式源可检查 |
| F：后续扩展 | GitHub Actions、macOS、其他架构 | 各自通过实机验收后启用能力 |

关键测试清单：

- 版本：高于、等于、低于当前版本，`0.10.0 > 0.9.0`，预发布不推送给正式版。
- 匹配：Windows/Mac 互不串包，x64/arm64 不误选，NSIS/portable 不混用，未来 Universal 兼容规则。
- 缺包：新版只有 Windows 时 Mac 不显示可更新；缺元数据、文件缺失、目标信息冲突均停止安装。
- 异常：离线、超时、限流、下载中断、磁盘空间不足、文件校验失败；失败不得伪装成最新版本。
- 状态：重复检查/下载合并，页面重挂载正确恢复快照，关闭面板不影响下载，旧事件不覆盖新状态。
- 安装：忙碌时禁止重启；新任务与安装互斥；托盘隐藏逻辑不拦截更新退出；普通退出不自动安装。
- 数据：同一系统账号升级后凭证、历史、AI 配置和桌面设置仍可用；涉及迁移时单独验收。
- 便携：只有下载入口，没有安装器动作；切换为新版 EXE 后继续使用原用户数据。
- 完整链路：必须用实际安装的旧版升级到更高版本；仅开发模式模拟或构建通过不足以证明自动更新可用。

新增测试聚焦版本与目标选择、状态转换、IPC 校验和退出协调；沿用现有类型检查、单元测试及相关桌面回归。首次带更新能力的版本本身仍需用户手动安装，之后才能检测下一版。

## 10. 实施前需复核的事项
